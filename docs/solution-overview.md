# 完整解决方案分解

## 第一部分：竞赛背景与任务定义

### AIMO3 竞赛概况

**AI Mathematical Olympiad - Progress Prize 3** 是 Kaggle 上的数学推理竞赛，时间跨度从 2025 年 11 月 20 日至 2026 年 4 月 15 日，目标是推动开源模型在奥林匹克级数学推理上的能力提升。

本届竞赛的关键特性：

1. **题目难度**：从国家级数学竞赛到 IMO 标准
2. **答案形式**：[0, 99999] 范围内的非负整数
3. **数据集规模**：
   - 50 道公开测试题（用于 public leaderboard）
   - 50 道私有测试题（用于比赛结束后的 private rerun）
   - 10 道参考题（供学习理解题型）
4. **题目形式**：纯 LaTeX 文本，无图片示意

### 评估机制的独特性

AIMO3 采用了不同于常规竞赛的评估方式：

**标准评分**（Public Leaderboard）
- 简单 accuracy：答对得 1 分，答错得 0 分

**私榜双路 Rerun 评分**（Private Leaderboard）
- 比赛结束后，官方会在 50 道私有题上**运行提交 notebook 两次**
- 将两次预测拼接后评分规则：
  - 两次都答对：1 分
  - 一次答对一次答错：0.5 分
  - 两次都答错：0 分

这个评分机制有深远影响：
- 不仅考验单次推理能力，还考验**跨 rerun 的稳定性**
- 鼓励构建**可复现、低方差的系统**而非追求极限准确度
- 对运行时环境、资源管理、随机种子控制提出高要求

## 第二部分：解决方案总体思路

### 核心目标

在 Kaggle 离线 Notebook 约束下，构建一个：
- **准确**：单次推理准确率尽可能高
- **稳定**：两次 rerun 间结果高度一致
- **可靠**：严格时间和资源约束内稳定运行
- **有效**：充分利用有限 GPU 显存和计算时间

的数学推理系统。

### 设计哲学

不同于"让模型写更多推理"的思路，本方案核心理念是：

> **强推理模型 + 可执行工具 + 多样化采样 + 置信度加权聚合 + 严格运行时工程**

这个模式认识到：
1. **数学问题需要推理与计算结合**：LLM 擅长高层结构和思路，但低层计算容易出错
2. **单链推理有方差**：不同随机种子会导致模型走上不同推理路径，部分路径失败
3. **置信度信号有价值**：模型生成时的 logprobs 反映了其自身的不确定性
4. **工程细节决定稳定性**：资源清理、时间管理、依赖隔离等工程措施比算法本身更影响 rerun 稳定性

## 第三部分：关键技术组件

### 1. 本地推理服务（vLLM）

**为什么不直接在 Python 中加载模型？**
- vLLM 提供 OpenAI 兼容 API 接口，推理清晰且可控
- 支持流式输出、KV Cache 复用、Prefix Caching
- 性能监控和调度更透明
- 与工具调用协议（Harmony）的集成更稳定

**核心参数**：
```yaml
max_model_len: 65536              # 支持较长上下文
kv_cache_dtype: fp8_e4m3         # 降低显存占用
enable_prefix_caching: true      # 多路径共享系统提示
async_scheduling: true           # 提升并发吞吐
gpu_memory_utilization: 0.96     # 激进显存利用
```

### 2. 工具调用与 Harmony 协议

**问题**：数学问题常需要精确计算，LLM 容易出现计算错误

**解决方案**：
- 让 LLM 生成 Python 代码
- 在持久 Jupyter kernel 中执行
- 返回结果给 LLM 继续推理

**Harmony 协议**：
- GPT-OSS 的原生工具调用协议（不是标准 OpenAI function calling）
- 通过特殊 token 序列表达工具调用意图
- 需要特定的 `openai_harmony` 库解析

**持久内核池**：
- 预启动 16 个 Jupyter kernel
- 避免每次工具调用都重新启动 Python
- 每条推理链独占一个 kernel，防止状态污染
- 推理结束后执行 `%reset -f` 并重导入库

### 3. 多路径并行推理

**并行度**：每题 8 次独立尝试（attempt）

**为什么是 8？**
- 权衡：更多路径 → 更好覆盖但时间增加
- 8 条路径 + early stop @4 票 = 平衡点

**Early Stop 机制**：
- 当任一答案累积到 4 票时立即停止
- 理由：8 条路径中 4 票意味着该答案不可能被反超
- 效果：节省尾部推理时间，同时保持高自一致性要求

**种子管理**：
- 每条路径使用不同 seed
- 确保采样多样化，而非 8 条完全相同的推理

### 4. 熵加权自一致性投票

**传统多数投票的问题**：
- 无法区分"8 条低质量路径都答 X"与"1 条高置信路径答 X"
- 对大答案空间 [0, 99999] 无力

**本方案的熵加权方案**：

每条路径在生成时保存 top-k logprobs，转换为置信度指标：

```
综合置信度 = f(
    平均 Shannon 熵,
    位置加权熵（接近答案的 token 权重更高）,
    熵的标准差（惩罚置信度波动）,
    高熵占比（惩罚长期不确定性）,
    低熵连续段奖励（奖励稳定输出）
)
```

最终投票：
```
每条路径的权重 = 1 / 综合熵值
最终答案 = argmax(sum_of_weights)
```

效果：将"不确定性信号"纳入决策，比盲目多数投票更有效。

### 5. 答案抽取

**规则顺序**：
1. 优先匹配 `\boxed{N}` 格式（标准数学习题答案形式）
2. 备用匹配 `final answer is N` 等自然语言模式
3. 去除数字中的千位符（逗号）
4. 验证答案在 [0, 99999] 范围内
5. 所有路径都无有效答案 → 返回 0

### 6. 动态时间预算

**为什么需要时间预算？**
- Kaggle 限制总运行时间 5 小时 (~17,400 秒)
- 50 道题不能简单平均分配（不同题难度差异大）
- 需要确保所有题都能被尝试

**预算策略**：
```
总预算: 17,400 秒
每题最少: 270 秒（保证每题至少能推理）
每题最多: 900 秒（防止某题过度占用）

实时预算计算：
已用时 + 剩余题数 × 270 = 下一题上界
```

## 第四部分：工程优化

### 1. 冷启动优化

**问题**：模型首次加载很慢

**解决方案**：
- 在 vLLM 启动前，多线程预读模型权重文件
- 将权重预热到 OS PageCache
- 减少实际推理时因磁盘 I/O 的停顿

### 2. 内存管理

**为什么需要显式清理？**
- 长时间运行的 Notebook 会累积内存碎片
- 16 个 Jupyter kernel 的内存占用需要主动回收

**策略**：
```python
# 推理前：禁用 GC 减少推理中的停顿
gc.disable()

# 单题结束：主动回收
gc.collect()
gc.enable()

# 推理结束：
每个 kernel 执行 %reset -f
关闭持久连接
显式删除大对象
```

### 3. 依赖隔离

**问题**：Kaggle 正式 rerun 环境不能联网安装

**解决方案**：
- 将所有依赖打包为 `wheels.tar.gz`
- 提交时包含在输入数据集中
- 推理时解压并 `pip install --no-index --find-links` 安装

## 第五部分：可复现性设计

### 为什么关注可复现性？

双路 rerun 评分机制意味着：**同一 Notebook 在同一数据上跑两次，需要尽可能返回相同答案**

### 可复现性的威胁

1. **浮点运算的非确定性**：不同 GPU 批次的浮点加法顺序可能不同
2. **多线程竞态**：并发操作的顺序不保证
3. **随机种子泄漏**：某个库静默使用了非控制的随机源
4. **系统状态**：内存布局、缓存状态等影响

### 应对策略

1. **固定所有 seed**：
   ```python
   torch.manual_seed(seed)
   np.random.seed(seed)
   random.seed(seed)
   torch.cuda.manual_seed_all(seed)
   ```

2. **禁用非确定性操作**：
   ```python
   torch.backends.cudnn.deterministic = True
   torch.use_deterministic_algorithms(True)
   ```

3. **单线程推理**：并行 attempt 通过不同 seed 而非真正并发实现
   
4. **环境变量固定**：
   ```python
   os.environ['CUBLAS_WORKSPACE_CONFIG'] = ':16:8'
   os.environ['CUDA_LAUNCH_BLOCKING'] = '1'
   ```

## 第六部分：性能指标与可迁移性

### 本方案的核心贡献

| 维度 | 贡献 |
|------|------|
| **算法创新** | 熵加权自一致性投票在大答案空间中的有效性 |
| **工程创新** | Kaggle 离线环境下的冷启动和显存优化 |
| **系统设计** | 工具调用、时间预算、资源管理的集成方案 |

### 可迁移模式

此解决方案中的多个模式可迁移到其他推理任务：

1. **工具增强推理** → 代码生成、数据分析等需要执行的任务
2. **多样化采样 + 置信度聚合** → 任何生成式任务中提升稳定性
3. **时间/资源动态预算** → 多任务批处理系统
4. **冷启动优化** → 任何包含模型加载的系统

### 适用场景

该模式最适合：
- 推理链长，最终答案短的任务（数学、代码、符号推理）
- 有可执行验证工具的领域（可精确检验答案）
- 需要稳定性而非极限准确度的应用
- 资源受限的环境（单 GPU、时间限制）
